### Security — this is the most important section

Run via Supabase's advisor tooling against project `fqsqoxsosavjhdsvfevk`:

- **~25 dashboard/console views use `SECURITY DEFINER`** (ERROR level) — they run with the view creator's privileges rather than the querying user's, bypassing RLS.
- **RLS is fully disabled** (ERROR level) on `actions`, `outcomes`, `engagement_events`, `documents`, plus the backup tables `pipeline_runs_bak`, `pipeline_errors_bak`, `agent_inputs_bak`.
- This matters specifically because **both dashboard HTML files embed the Supabase anon key directly in client-side JavaScript** (`SUPABASE_KEY` constant), and the README already flags this as "internal only, don't host publicly." With RLS disabled on those tables, anyone who has that key — which is sitting in plain text in a static HTML file — can read or write those tables directly via the Supabase REST API, not just through the dashboard's intended views.
- `app_config` has an "always true" RLS policy granting **UPDATE to anon** (`app_config_anon_update`). This is intentional — it's what powers the dashboard's Settings tab — but it means anyone with the anon key can rewrite `tracking_base_url`, `ga4_property_id`, or `when_engine_url` directly, bypassing the UI entirely.
- I verified this last point concretely: the "shared" dashboard (`pipeline-control-tower-shared.html`) disables the Settings inputs and hides the Save button in the HTML, and its caption literally says "Read-only shared view." But it embeds the **exact same anon key** with the **exact same UPDATE grant**, and the page's `saveSettings()`/`patchConfig()` JavaScript functions are still present in the file. The "lock" on the shared copy is cosmetic (a disabled `<input>` attribute) — it is not a real permissions boundary. Anyone who opens dev tools, or just sends a raw `PATCH` request with the embedded key, can still rewrite `app_config` from the "read-only" copy.
- Separately: the brief/action approval links the dashboard opens (`/webhook/brief-approval?id=…&action=approve`, `/webhook/action-approval?id=…&action=approve`) are **plain unauthenticated GET requests** — I checked both workflow JSONs and neither webhook node has any auth configured. Anyone with (or guessing) a small integer `id` can approve or reject any brief or action with no credentials.
- Lower severity: `pipeline_runs` and `pipeline_errors` have RLS enabled but zero policies (INFO — effectively locked down by default, which is fine and is why the SECURITY DEFINER views are doing the actual data exposure work for these two tables).

**Net read:** the security model currently rests entirely on "the anon key is hard to find," not on RLS or auth. That's consistent with an internal-tool design but is worth being deliberate about, especially since the "shared" dashboard is explicitly meant to be handed to other people.

> **2026-06-28 — Remediated.** Three changes, keeping the static-HTML/no-login model intact:
> 1. **RLS + grants on the exposed tables.** Enabled RLS on `actions`, `outcomes`, `engagement_events`, `documents`, `pipeline_runs_bak`, `pipeline_errors_bak`, `agent_inputs_bak` (all previously had RLS fully disabled), and revoked all anon/authenticated grants on these plus `pipeline_runs`/`pipeline_errors` (already RLS-on-no-policy, but still had stray grants that would've become exploitable the moment a policy was added). Default-deny is safe here because every legitimate read goes through a `SECURITY DEFINER` view (bypasses base-table grants/RLS via the view owner) and every legitimate write goes through n8n's Postgres credential, which connects as `postgres` — confirmed `rolbypassrls = true`, so unaffected by RLS. Fixed `agent_inputs`'s `service_role_all` policy, which was named for `service_role` but actually granted to `{public}` (i.e. anon + authenticated too) — replaced with a policy genuinely scoped to `service_role`.
> 2. **Scoped the `app_config` anon UPDATE.** The policy now only matches `key IN ('tracking_base_url', 'ga4_property_id')` — the two keys the dashboard's Settings tab actually edits — and the anon grant is now column-level (`UPDATE (value)` only, matching what `patchConfig()` actually sends). This closes a real gap: `when_engine_url` (controls where rejected briefs/actions get forwarded) was previously anon-writable via a raw PATCH even though no UI ever exposed that. Verified live: anon can still update `tracking_base_url`/`ga4_property_id`, cannot touch `when_engine_url`.
> 3. **Signed the approval webhooks.** `/webhook/brief-approval` and `/webhook/action-approval` now require an HMAC-SHA256 `sig` query param (scoped per-webhook, computed server-side at link-generation time and re-verified on receipt with `crypto.timingSafeEqual`); requests with a missing/wrong signature get a 403 instead of reaching the approve/reject logic. Also fixed: the `reason` query param (used in `Action Approval Handler`'s `Mark Cancelled` Postgres node, which builds its query via string interpolation) is now whitelist-sanitized to `[a-zA-Z0-9 _-]` before use — closing the SQL-injection path that existed in that node. Verified via `test_workflow`: valid signatures route to the approve/reject path, invalid ones route to the 403 responder, and a SQL-injection-shaped `reason` gets stripped clean before it could reach the vulnerable node.
>
> Residual, out of scope for this pass: the ~25 `SECURITY DEFINER` console/dashboard views (ERROR level) are the intended access mechanism in this no-auth design, not a bug — removing `SECURITY DEFINER` from them would break the dashboard's reads entirely. `match_documents`'s mutable search_path and the `vector` extension living in `public` are both pre-existing, low-severity, and unrelated to the access-control gaps above.
>
> **2026-06-28 — second pass, found while building the campaigns subsystem (below).** Every pre-existing dashboard/console view (25 of them) still had full `INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER` granted to `anon`/`authenticated` — only `app_config` was correctly SELECT-scoped. Most of these views are joins/aggregates/`GROUP BY`/`LIMIT`, so Postgres's auto-updatable-view rules block writes through them regardless of grant. But `feedback_for_tabita` and `feedback_for_engine` are plain single-table `SELECT ... FROM actions WHERE ... ORDER BY ...` views with no aggregation, `GROUP BY`, `DISTINCT`, or `LIMIT` — which makes them genuinely auto-updatable. With the broad grant in place, `anon` could `INSERT`/`UPDATE`/`DELETE` directly against `actions` through either view, fully bypassing the RLS lockdown from the first pass. Fixed by revoking all and re-granting `SELECT` only on all 25 views (migration `lock_dashboard_views_to_select_only`). Verified: `role_table_grants` now shows `{SELECT}` only on every dashboard/console view, and a follow-up `get_advisors` security scan came back with no new findings — only the same pre-existing/accepted `security_definer_view`, `rls_enabled_no_policy`, `function_search_path_mutable`, and `extension_in_public` items.

### New subsystem: campaigns & cadences (2026-06-28)

Added multi-step cadence tracking on top of the existing single-shot `actions` table, per the roadmap discussion about evolving the Action Layer into multi-touch outreach:

- **Tables:** `campaigns` (one per account/run, `status` active/completed/cancelled) and `cadence_steps` (ordered steps per campaign — `step_number`, `delay_days`, `scheduled_for`, the same action-shape columns as `actions` — `account/action_type/target/reason/hypothesis/predicted_metric/predicted_direction/threshold/window_days/utm_campaign/tracked_url/outreach_draft` — plus `status` pending/recommended/executed/measured/cancelled/skipped and `action_id` once a step is promoted to a real action). `actions` gained a `campaign_id` FK back to `campaigns`.
- **Trigger:** `trg_sync_cadence_step_status` (AFTER UPDATE on `actions`) calls `sync_cadence_step_status()`, which mirrors an action's status onto its originating `cadence_steps` row whenever it changes — so approving/cancelling an action in the existing approval flow automatically updates the cadence view without any new approval-handler logic.
- **Workflow wiring:** Brief Approval Handler now creates a `campaigns` row + its `cadence_steps` on approval (instead of just one `actions` row). A new workflow, **Cadence Scheduler** (`LcZx5U9dVmOwaGQl`, daily 06:30 schedule trigger), finds due steps (`scheduled_for <= now()` and `status='pending'`), inserts each as a real `actions` row, marks the source `cadence_steps` row `recommended`, and emails an HMAC-signed approval link per step using the same signing scheme as the other approval emails — so due cadence steps flow into the existing approval inbox rather than a separate one.
- **Views:** `dashboard_campaigns` (per-campaign rollup: total/completed/awaiting-approval/upcoming/cancelled/skipped step counts, next step due) and `dashboard_cadence_steps` (flat per-step list with account/step/delay/scheduled time/status). Both `SECURITY DEFINER`, both granted `SELECT` only to `anon`/`authenticated` (caught and fixed an initial overgrant on these two — see the security note above).
- **Dashboard:** new "Campaigns" tab in both `pipeline-control-tower.html` and `-shared.html` — 4 KPI cards plus a campaigns table and a cadence-steps table, both backed by the two views above.

### New subsystem: Salesforce sync prototype (2026-06-28)

Follow-up to a strategic question about repositioning the project as an orchestration layer over CRM/MAP tools (Salesforce, Marketo) rather than a standalone campaign engine. Scoped down to a concrete, testable prototype:

- **Decision: Salesforce only, Supabase stays source of truth.** Salesforce was prototyped because a working credential already exists in n8n; Marketo was scoped out entirely — no org, no credentials, no native n8n node. Supabase's `campaigns`/`cadence_steps` remain authoritative; Salesforce is a one-way synced execution layer underneath them, not a replacement. Nothing reads back from Salesforce into Supabase.
- **Mechanism discovery:** n8n's Salesforce node has no first-class "Campaign" resource (only Account/Contact/Lead/Opportunity/Case/Task/etc., plus a generic `customObject` resource meant for true `__c` custom objects). Tested empirically against the live Salesforce credential: passing the standard object API name `"Campaign"` directly into the `customObject` field works for `create` — confirmed via a disposable probe workflow that created a real Campaign (`701OQ00000cm87LYAQ`) and then deleted it through the same mechanism's `delete` operation (`success:true`). Field values are set via `customFieldsUi.customFieldsValues: [{fieldId, value}]`, where `fieldId` also accepts standard field API names (`Name`, `Status`, `Type`) as free text. This closes out the need for an HTTP Request fallback (which would have needed the Salesforce instance base URL).
- **Schema (migration `add_salesforce_sync_fields`):** `campaigns` gained `salesforce_campaign_id`, `salesforce_sync_status` (`pending`/`synced`/`error`/`skipped`, default `pending`), `salesforce_synced_at`, `salesforce_sync_error`. `actions` gained a reserved, currently-unpopulated `salesforce_task_id` column (for a likely future per-action Task sync, tied to the existing disabled Find-Account/Create-Task nodes in Action Approval Handler) — added now to avoid a second migration later.
- **Workflow wiring:** Brief Approval Handler's existing `Insert Campaign` node got a second, parallel output branch (the original `Insert Campaign → Recommend Action → …` cadence chain is untouched): `Create Salesforce Campaign` (Salesforce node, `customObject`/`create`/`Campaign`, `onError: continueErrorOutput`) → success branch `Mark Salesforce Synced` (Postgres UPDATE, sets `salesforce_campaign_id`/`synced`/`salesforce_synced_at`), error branch `Mark Salesforce Sync Error` (Postgres UPDATE, sets `error` + the Salesforce error message via `queryReplacement` to avoid string-concatenation injection). A Salesforce failure can't break brief approval or cadence-step creation — it's a sibling branch, not a step in the existing chain.
- **Caught while building:** the new `Mark Salesforce Synced` node's query was missing the leading `=` n8n requires to treat a string as an expression (`MISSING_EXPRESSION_PREFIX`) — fixed before testing. (Two pre-existing, already-proven-working nodes — `Mark Brief Approved`, `Mark Brief Rejected` — have the same missing-prefix pattern and were deliberately left alone; touching working production nodes outside this change's scope wasn't worth the risk.)

### New subsystem: campaign templates (2026-06-28)

Follow-up to the user's "I don't own a website to turn on real tracking, I'm just an intern" constraint — instead of a manual template picker, made cadence selection automatic from signals already on the brief, via `AskUserQuestion` confirming "automatic by brief signal" over a manual dropdown or single default.

- **Table:** `campaign_templates` (`id`, `key`, `name`, `priority`, `match_urgency_in text[]`, `match_coverage_in text[]`, `match_stage_contains text`, `steps jsonb`). NULL on any match column means wildcard. Seeded 4 rows: `urgent_fast_track` (priority 10, 3 steps), `narrow_coverage_nurture` (15, 4 steps), `cold_outreach` (20, 5 steps), `warm_reengage` (99, all match columns NULL — catch-all, 5 steps). Each step: `{action_type, delay_days, reason}`.
- **Workflow wiring (Brief Approval Handler):** new Postgres node `Select Campaign Template` runs `... ORDER BY priority ASC LIMIT 1` with `$1/$2/$3` bound to the brief's `when_urgency`/`coverage_label`/`when_stage`, sits between `Get Config` and `Insert Campaign`. `Insert Campaign` now also writes `template_key`. `Recommend Action` was rewritten to map the matched template's `steps` into the action plan instead of a hardcoded COLD/not-COLD `plan` array — same output shape (campaign_id/run_id/account/target/action_type/priority/reason/delay_days/scheduled_for/hypothesis/predicted_metric/utm_campaign/tracked_url/outreach_draft/status), so nothing downstream changed. ### Security: third occurrence of the default-ACL / auto-updatable-view leak (2026-06-28)

Found while creating the two views above — same bug class as the `feedback_for_tabita`/`feedback_for_engine` incident in the "second pass" note earlier in this doc, but this is a **separate, still-unfixed root cause**: that prior fix revoked the over-grant on the *existing* views at the time, it did not remove the default ACL rule that keeps producing this on every *new* view.

- **Root cause confirmed via `pg_default_acl`:** this project's `public` schema has `ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public GRANT ALL ON TABLES TO anon, authenticated`. Every newly created relation — table or view — gets full `INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER` for `anon`/`authenticated` automatically at creation time, regardless of any `GRANT SELECT` issued afterward (the explicit grant only adds to the default-ACL grant, it doesn't replace it).
- **Why it's exploitable:** `console_open_actions` and `console_recent_engagement` are both plain single-table `SELECT ... FROM x WHERE ... ORDER BY ...` views with no join/aggregate/`DISTINCT`/`GROUP BY` — exactly the shape Postgres treats as auto-updatable. So `anon` could `INSERT`/`UPDATE`/`DELETE` straight through either view into the locked-down base tables `actions`/`engagement_events`, fully bypassing their RLS lockdown from the first security pass.
- **Fix applied:** migration `lock_down_new_console_views_select_only` — explicit `REVOKE ALL ... FROM anon, authenticated, PUBLIC` on both views, then re-`GRANT SELECT`. Verified via `information_schema.role_table_grants` before (full CRUD) and after (SELECT only).
- **Not yet fixed: the default ACL rule itself.** This is the third time this exact class of bug has shipped in this project (1st: the original 25 dashboard views; 2nd: `feedback_for_tabita`/`feedback_for_engine`; 3rd: these two). Each time the fix has been per-view (revoke-then-grant), not a removal of the `ALTER DEFAULT PRIVILEGES` rule that keeps causing it. **Recommended next step:** either drop the default-ACL rule entirely (`ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public REVOKE ALL ON TABLES FROM anon, authenticated`) and grant SELECT explicitly per-view going forward, or add a standing checklist item — any future `CREATE VIEW`/`CREATE TABLE` in this schema must be followed by an explicit grant audit via `role_table_grants` before being wired into a public-facing dashboard. Documented in `supabase/schema.sql`'s grant-block comment and in memory (`supabase_default_acl_leak`).

### New subsystem: Adaptive Decision Engine (Phase 4, 2026-06-29)

Every other phase so far automates *getting* a cadence built and executed; nothing yet reacted to how a step actually performed once it was measured — a campaign that already converted kept running its remaining steps, dead campaigns kept retrying the same channel forever, and warm-but-unconverted leads sat on whatever channel the template/AI happened to pick first. This phase closes that loop with a small, explicit rule engine over `outcomes`.

- **New, standalone workflow** rather than a modification of Action Outcome Measurement's existing branches — chosen to avoid regression risk on a live production workflow and the cross-branch item-reference ambiguity that would come from reading another branch's lineage mid-loop. **Adaptive Decision Engine** (`tGYW1gMBXQrC3bQ6`, daily 06:15, 15 minutes after Action Outcome Measurement runs): `Get Recently Measured Steps` (Postgres — outcomes measured in the last day, joined back to their `cadence_steps`/`campaigns`, filtered to `cs.adaptive_action is null` so nothing is ever re-adjudicated) → `Loop Measured Steps` (`splitInBatches`, size 1) → per step: `Get Campaign Signal` (Postgres — remaining pending steps, the next pending step's id/channel, whether a high-touch channel has been used yet, total engagement-event count for the campaign) → `Decide Adaptive Action` (Code — pure rule evaluation, builds a raw multi-statement SQL string) → `Apply Adaptive Decision` (Postgres — executes that SQL) → next batch.
- **Four rules, in priority order:** (1) **stop** — if the step's outcome was `met`, cancel every remaining `pending`/`recommended` step on the campaign and mark the campaign `completed`/`completion_reason='goal_met'`; goal achieved elsewhere makes further cadence steps wasted outreach. (2) **pause** — if the campaign has zero `engagement_events` and there's a next pending step, push that step's `scheduled_for` out 7 days; no signal at all yet means hitting the same dead lead on schedule is unlikely to help. (3) **escalate** — if there's been engagement but no conversion and the next pending step is on a low-touch channel (email/content_download/landing_page/ads/webinar/linkedin_engage), bump that step to a higher-touch channel — `linkedin_connect` if no high-touch channel has been used yet on this campaign, else `phone`; warm-but-stalled leads get a more personal channel instead of repeating what already isn't converting. (4) **reviewed** — none of the above; no-op, just stamped so it isn't re-evaluated. Every branch stamps the *originating* step's new `cadence_steps.adaptive_action`/`adaptive_reason` columns, which is what makes rule (1)'s filter idempotent without a separate tracking table.
- **Deliberately additive, not invasive:** pause/escalate work by mutating the *next* step's `scheduled_for`/`action_type` — Cadence Scheduler's existing `status='pending' and scheduled_for <= now()` query picks up both changes automatically, so zero changes were needed to Cadence Scheduler itself.
- **Schema (migration `phase4_adaptive_decision_columns`):** `cadence_steps` gained `adaptive_action text`/`adaptive_reason text`; `campaigns` gained `completion_reason text`. Note: the column comment on `adaptive_action` only lists `escalated`/`paused`/`stopped` — the fourth real value, `reviewed`, was added to the code after the comment was written and the comment hasn't been corrected yet (cosmetic, not a behavior bug).
- **Verification:** built 4 disposable test campaigns (`TEST_PHASE4_A`–`D`, one per rule branch, via direct SQL inserts — campaign → action → cadence_steps → outcome → engagement_events as needed), ran the published workflow once via `execute_workflow` (execution succeeded), then independently queried Postgres post-run state for all 4 campaigns and confirmed exact expected mutations: A's remaining steps cancelled + campaign completed/goal_met, B's next step pushed 7 days, C's next step's `action_type` swapped to the expected escalation target, D stamped `reviewed` with no other change. Re-ran the source query afterward and got 0 rows back, confirming the `adaptive_action is null` filter makes re-runs a no-op. All 4 test campaigns and their dependent rows deleted afterward; verified zero residual under the `TEST_PHASE4_%` tag.
- **Dashboard:** `dashboard_cadence_steps` view and both `pipeline-control-tower.html`/`-shared.html` Cadence steps tables gained "Adaptive" (action) / "Adaptive reason" columns, same pattern as Phase 5's Channel/Why columns.
- **Verification:** two full `execute_workflow` (manual mode — real credentials, real OpenAI call, real DB writes, no publish required) runs against the disposable test account, the second confirming the JSON-mode fix; DB rows for both runs inspected directly via `execute_sql` and the test campaign/action/cadence_steps/pipeline_runs rows deleted afterward (verified zero residual). Published to make this live in production after the second run came back clean.
- **Follow-up, same day: `dashboard_channel_source_performance` view.** Added to answer "did the AI's channel picks actually outperform the template's?" — same shape as `dashboard_hypothesis_winrate` but grouped by `channel_source` instead of `action_type` (executed/measured/met/win_rate_pct). Added now rather than later specifically *because* the system is still pre-traffic (`outcomes`: 0 rows, only 3 of 50 actions ever `executed`) — confirmed empty/near-empty on creation as expected, but it's wired into both dashboards and ready the moment real executed/measured actions accumulate, rather than a forgotten TODO. Surfaced as a new chart ("AI vs. template channel picks — win rate by source") on both `pipeline-control-tower.html` and `-shared.html`, right after the existing channel-performance chart.

### Lead / Campaign Member sync — hardened, re-enabled, and published (2026-06-29)

User reframed priorities directly: the 10-phase roadmap is secondary to the actual goal — automate Salesforce lead creation/maintenance and get feedback. Picked back up the 5 Salesforce-writing nodes in Action Approval Handler that were disabled 2026-06-28 pending review (see above) and re-tested for real this time, rather than re-enabling on the strength of the original (simulated-pin-data) test alone. That decision paid off — live execution against real Salesforce surfaced two structural bugs the original build/test pass had no way to catch:

- **Found: `Find Existing Lead`'s SOQL `search`/`query` operation does not loop per input item.** Unlike most n8n nodes, this Salesforce operation runs once per node-execution regardless of how many items are fed in — with 2 confirmed buying-group contacts in one item batch, it ran once, collapsed to a single empty placeholder output item (`alwaysOutputData:true`), and `pairedItem` referenced both original items at once. Anything downstream assuming per-contact search results silently got garbage.
- **Found: `Create Lead` read `company`/`lastname`/`firstname`/`title`/`focus_area` from the wrong node.** It used bare `$json.*`, which after `Find Existing Lead` only carries SOQL result columns (`Id`) — never the original contact fields. Confirmed via a real Salesforce API error: `"Required fields are missing: [LastName, Company]"`. This means the "create new Lead" path had likely never actually worked, even when the 5 nodes were "tested" before being disabled — pinned/simulated test data can't catch a wrong-node field reference like this.
- **Fix: wrapped the branch in a `splitInBatches` loop** (`batchSize:1`, new node "Loop Contacts" between `Extract Confirmed Contacts` and `Find Existing Lead`; loop body's two terminal nodes — `Add Existing Lead To Campaign` and `Add New Lead To Campaign` — wired back into it to pull the next contact). Copied this pattern directly from the Adaptive Decision Engine's proven "Loop Measured Steps" node rather than inventing a new shape. Also fixed `Create Lead`'s 5 fields to read `$('Extract Confirmed Contacts').item.json.*` instead of `$json.*` — the same explicit-node-reference pattern `Add Existing/New Lead To Campaign`'s `campaignId` already used correctly.
- **Found and closed a second idempotency gap.** The existing guard (`Mark Executed`'s `WHERE ... AND status <> 'executed'`, added when this branch was first built) correctly stopped the Lead-sync side on a replayed approve-link hit, but `Create a task` and `Send Action to Rep` sat on a separate, unguarded connection straight off `Mark Executed` — a replay still created a real (garbage-content) Salesforce Task and sent a duplicate rep email, because n8n's Postgres node emits a placeholder `{success:true}` item on a 0-row UPDATE rather than 0 items. Added a new `Action Updated?` IF node (checks `$json.id` notEmpty) gating both `Create a task` and `Extract Confirmed Contacts`, with the false branch routed to a new `Respond Already Processed` node instead of silently falling through.
- **Hardened the dedup match.** `Find Existing Lead`'s SOQL match grew from `LastName`+`Company` to `FirstName`+`LastName`+`Company`, closing a real collision risk (two different buying-group contacts sharing a surname at the same account would otherwise have collapsed onto one Salesforce Lead).
- **Verified end-to-end against disposable data** (`ZZZ-QA-LEADSYNC-TEST` — `pipeline_runs`/`campaigns`/`actions` rows, deleted after): one execution created two real, distinct Salesforce Leads (Jordan Vega, Taylor Vega) with correct field values; a second execution against a fresh action referencing the same two contacts correctly found and reused both existing Leads via the hardened dedup match instead of duplicating them; a replay of an already-executed action's approve link correctly short-circuited at `Action Updated?` with zero side effects (no duplicate Lead/Task/email). `onError: continueRegularOutput` on every Salesforce node in the branch was independently confirmed working — a deliberately-malformed test Salesforce Campaign ID caused expected, isolated `MALFORMED_ID` failures on `Create a task`/`Add Existing|New Lead To Campaign` without blocking `Send Action to Rep`/`Respond Approved`. Test Salesforce records (2 Leads, 1 Task) deleted afterward via a disposable probe workflow using the native `lead.delete`/`task.delete` operations, then archived.
- **Published.** Draft/active divergence checked and confirmed (active still had all 5 nodes disabled, no loop, no idempotency gate) before `publish_workflow` — consistent with every prior workflow edit in this project; see the repeated "Takeaway" note above.

Still open, unchanged from before: no real contact emails anywhere in `raw_payload.buying_group` (Lead `upsert` with a custom External ID field remains blocked on that), and `campaigns`/`actions` in production still have zero rows that have reached `executed` through this branch with a *real* (non-test) Salesforce Campaign — worth a spot-check the first time that happens organically.

### New subsystem: Salesforce Activities read-back (2026-06-30)

Closes a gap on the user's own self-authored roadmap: Salesforce was a one-way sync (Supabase → Salesforce, Leads/Campaigns/Tasks created but never read back) and there was no path for what reps actually do on a Lead in Salesforce — logging a call, a note, a follow-up Task — to flow back into this system's measurement layer. **Two Code-node bugs found and fixed during build/test, both the same root cause — an n8n Code node's `mode` parameter is not safely inferred and must always be set explicitly:**

Same fix: explicit `mode: 'runOnceForAllItems'` + manual loop. Caught both times via `test_workflow` + `get_execution` item-count inspection, not by the tool surfacing an error — an unset `mode` fails silently, it does not fail loudly. ### Coworker pressure-test fixes: template audit trail, hard/soft scoring, SF Campaign write-back, diminishing returns (2026-06-30)

A coworker (Jocelyn) pressure-tested the pipeline end to end and surfaced a 6-item gap list. Items 5 (Lead/Campaign Member sync) and 6 (a non-technical item) were already covered or out of scope; this pass closed the remaining four:

- **Item 1 — template-selection audit trail.** `campaigns` gained `template_match_trace jsonb`. Brief Approval Handler's `Select Campaign Template` query now returns every `campaign_templates` row that matched the brief (not just the winner), ranked by `priority`; a new code node, `Build Template Match Trace`, reduces that ranked list to `{matched_count, winner_key, winner_name, winner_priority, runner_ups, reason}` and `Insert Campaign` writes it alongside the existing `template_key`. `template_key` stays "what we picked"; `template_match_trace` is "why," including every runner-up that also matched and lost.
- **Item 2 — hard vs. soft signal separation.** `account_score` (view) now exposes `hard_points` and `soft_points` alongside the existing blended `score`: `hard_points` sums only events whose `engagement_events.source` is `ga4`, `gmail`, or `salesforce` (independently observed); `soft_points` sums only `source='manual'` (self-reported). - **Item 4 — diminishing returns on repeated soft signals.** `account_score`'s event-scoring CTE gained `occurrence_rank` (`row_number() OVER (PARTITION BY account, event_type ORDER BY occurred_at)`): the 1st occurrence of a given event type counts at full weight, the 2nd at 0.4x, the 3rd and beyond at 0x. Without this, a high volume of low-effort events (e.g. repeated `page_visit`/`email_open`) on one account could inflate its score without bound; now it plateaus.

**One bug found and fixed, affecting both items 1 and 2:** an editing pass on `Select Campaign Template` and `Gather Channel Context` (both Postgres nodes) used a path-based parameter edit that created a stray **nested duplicate key** — `parameters.parameters.query` — sitting alongside the real top-level `parameters.query` n8n actually executes. `get_workflow_details` still *looked* right at a glance (the new SQL was present in the JSON somewhere), but the live node kept running the old, pre-fix query underneath — silently making the item 1 and item 2 schema/SQL changes inert.
